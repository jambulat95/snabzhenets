# «Снабженец» — правила проекта

Правила одинаковы для человека и для ИИ-ассистента, который пишет код (`CLAUDE.md` и `AGENTS.md` — один и тот же текст). Нарушение правила — повод не принять изменение.

Контекст: архитектура — `docs/ARCHITECTURE.md`, план до защиты 14.11.2026 — `docs/PLAN.md`, источники демо-данных — `docs/SOURCES.md`.

## Карта репозитория

- `backend/app/ai/` — ИИ-слой, перенесён из A2A Маркет (шлюз моделей, разбор заявки, разбор писем, прайсы, фильтр инъекций, поиск).
- `backend/app/` — домен «Снабженца»: заявка, поставщики, переписка, цены, методика, документы, журнал.
- `backend/tests/` — тесты; `backend/eval/` — eval-наборы и скрипты для LLM-шагов.
- `data/replay/` — записанные открытые данные для офлайн-демо.

## Команды

```bash
cd backend && uv sync                     # окружение
cd backend && uv run pytest -q            # тесты
cd backend && uv run ruff check app tests # линтер
cd backend && uv run mypy                 # типы (strict для app/ai)
docker compose up -d --build              # база, Redis, почтовая песочница, API, воркер
curl localhost:8010/api/health            # проверка
cd backend && uv run python -m app.seed --reset && uv run python -u scripts/check_scenario.py  # сквозной демо-сценарий
```

Порты на хосте (не пересекаются с A2A Маркет): API 8010, PostgreSQL 5433, Redis 6380, SMTP 3025, IMAP 3143.

## 1. Продуктовые правила (не обсуждаются)

1. **Деньги, количества, сроки, проверки методики и НМЦК считает код, а не модель.** Модель извлекает и сопоставляет, код проверяет и считает. Денежные значения — только `Decimal`.
2. **Каждое число из внешнего источника проверяется по этому источнику.** Цену из письма код обязан найти в тексте письма, цену со страницы — в разметке или тексте страницы. Не нашёл — цена не принимается.
3. **Нет доказательства — нет цены в расчёте.** Доказательство — это файл в хранилище (sha256) плюс запись о нём в журнале.
4. **Агент не берёт обязательств.** Он не обещает заказ, ничего не подписывает, не проводит закупку и не называет поставщику цены конкурентов. Юридически значимые тексты — только из шаблонов, а не генерация модели.
5. **Две точки утверждения обязательны:** человек подтверждает спецификацию и утверждает обоснование. Код не может перевести заявку в `APPROVED` без действия пользователя с ролью `contract_manager`.
6. **Демо-режим по умолчанию.** При `DEMO_MODE=true` письма уходят только на `@demo.local`; проверка стоит в `MailPort` и покрыта тестом. Боевой режим включает только администратор, и первая рассылка требует подтверждения.
7. **Говорим только о том, что работает.** Эмулированное в интерфейсе помечено значком «демо», в документах — «в прототипе» или «в пилоте».

## 2. Работа с ИИ

1. Все вызовы моделей — только через шлюз `app.ai.gateway`, никаких прямых HTTP-запросов к провайдерам.
2. У каждого вызова есть pydantic-схема ответа. Ответ, не прошедший схему, — это ошибка, а не «примерно правильно».
3. Внешний текст (письма, страницы, вложения, текст заявки) передаётся модели только через `wrap_data` и проходит фильтр инъекций. Подозрительное — эскалация к человеку.
4. Промпты лежат файлами `prompts/<id>.v<N>.md`. Правка промпта — новая версия `N+1`, прогон eval и отчёт в `eval/reports/`. Старая версия не удаляется, пока есть записи в журнале с ней.
5. У каждого LLM-шага есть eval-набор и порог: разбор заявки ≥ 95% строк, письма — ≥ 95% цен, совпадение товара ≥ 90%, атаки — 0 пропусков. Порог ниже — изменение не принимается.
6. `temperature=0`. В журнал пишутся модель, версия промпта, токены и стоимость.
7. Перед облачной моделью ПДн маскируются (`pii.anonymize`). Для данных учреждения при необходимости — локальная Qwen.
8. Модель не выбирает поставщиков и не решает, допустима ли цена. Она только отвечает на узкий вопрос со схемой.

## 3. Архитектурные правила

1. Внешние системы — только через порты в `app/integrations/<имя>/`: `port.py` (Protocol), `live.py`, `replay.py` или `fake.py`. Домен импортирует только `port.py`.
2. `app/ai` и `app/integrations` не импортируют доменные модели.
3. Смена состояния заявки — только через `pipeline.transition()`: проверка допустимого перехода, запись в журнал и изменение в одной транзакции.
4. Побочные эффекты (письмо, загрузка страницы) — через outbox или задачу воркера, никогда внутри HTTP-запроса пользователя.
5. Задачи воркера идемпотентны: ключ (заявка, шаг, попытка). Повторный запуск не рассылает писем дважды.
6. Журнал только дополняется (триггер БД). Исправление — новая запись, а не правка старой.
7. Параметры методики — в профиле `methodology/profiles/*.yaml` со ссылкой на норму, а не константами в коде.
8. Новая таблица — только миграцией Alembic, ручные изменения схемы запрещены.

## 4. Внешние источники и этика

1. Сайты: только домены из allowlist, `robots.txt`, не чаще 1 запроса в 2 секунды на домен, User-Agent честно называет сервис. Капчу, вход и антибот-защиту не обходим: такого поставщика переводим на запрос по почте.
2. ЕИС, DaData, ФНС — по их правилам и лимитам, с кэшированием ответов.
3. В демо реальные поставщики видны (найдены в ЕИС), но вся переписка идёт с их «двойниками» в песочнице. В интерфейсе это помечено.
4. Персональные данные сотрудников поставщиков не собираем: только реквизиты юрлица и общий адрес для запросов.

## 5. Код и качество

1. Python 3.12+, полная типизация. Для `app/ai`, `app/methodology`, `app/quotes` — `mypy --strict`, для остального — `mypy` без ошибок в новом коде. `ruff` — конфигурация из A2A.
2. Идентификаторы — на английском; тексты интерфейса, сообщения пользователю, комментарии и документы — на русском.
3. Тесты:
   - unit — на каждое правило методики, расчёт НМЦК и CV, сверку чисел, переходы состояний;
   - контрактные — у каждого порта fake и live проходят один набор тестов (live — по флагу);
   - сквозной `scripts/check_scenario.py` — демо-сценарий от текста заявки до DOCX на replay-данных. Запускается в CI без сети.
4. Готово (Definition of Done) = код + тесты + eval (если менялся LLM-шаг) + сквозной сценарий зелёный + интерфейс показывает результат + запись в журнал есть.
5. Перед коммитом: `ruff`, `mypy`, `pytest`, `check_scenario`. CI повторяет то же самое.

## 6. Git

1. `main` всегда работоспособна: демо поднимается и сквозной сценарий проходит.
2. Ветки `feat/<тема>`, `fix/<тема>`; коммит — одно законченное изменение, сообщение на русском: `модуль: что сделано`.
3. Перенесённый из A2A код коммитится отдельным коммитом «перенос из A2A Маркет: <модуль>» без правок, правки — следующими коммитами. Так видно, что взято, а что написано.
4. `NOTICE.md` перечисляет перенесённые модули и авторов.
5. Секреты, `.env`, записи реальных писем и ПДн в репозиторий не попадают. Replay-данные ЕИС — это открытые сведения, их коммитить можно.

## 7. Демо и защита

1. Демо поднимается одной командой и работает без интернета.
2. Кнопки оператора: «Сбросить сценарий» (≤ 1 мин) и «Ускорить время» (таймеры напоминаний и срока сбора).
3. Сценарий защиты зафиксирован в `docs/DEMO.md`, и после каждого изменения он проходится вручную.
4. Фича, которая не работает надёжно, на защите не показывается и в интерфейс не попадает.
